# LHON 見え方シミュレータ 計画

視野マッパーで計測した見え方を、**晴眼者が体験できる形**で再現する機能の計画。

## 目的

レーベル遺伝性視神経症（LHON）は中心視野が障害され、視力が0.1程度まで低下する。
周辺視は比較的保たれるため、「見たいものだけが見えない」という状態になる。

この機能は、普通のテキストを読ませながら中心視野をぼかすことで、
**当事者が文章を読むときに何が起きているのかを、晴眼者が身体で理解する**ことを狙う。

決定的なのは**視線追従**であること。中心暗点は網膜に固定されているので、
目を動かしても一緒に動く。「横を見れば読める」ということが起きない。
画面中央を固定的にぼかすだけでは、視線を逸らせば読めてしまい、本質が伝わらない。

## 位置づけ（重要）

これは**シミュレーションであって、追体験ではない**。ドキュメントとUIの両方に明記する。

- 当事者は時間をかけて**偏心視（PRL: preferred retinal locus）**を獲得し、
  中心を外して見る技術を身につける。数分触っただけの晴眼者にはその適応がない
- 逆に、当事者が日常的に感じている疲労や読字速度の低下は、短時間の体験では再現されない
- したがってこの機能が示せるのは「**適応する前の、情報としての見えにくさ**」に限られる

視野マッパー本体と同じく、医療機器ではない旨の注記を出す。

## 段階

### Phase 0 — モック（パラメータで作る見え方）  ✅ 実装済み

計測データを使わず、中心ほどぼやける放射状のぼかしを手で作る。まずここまでで体験の骨格を確認する。

- 背景に**普通の日本語テキスト**（記事程度の分量、フォントサイズ可変）
- ぼかしプロファイル: 中心のσ最大 → 外側でσ0。パラメータは
  `centerSigmaPx` / `plateauDeg`（完全に見えない中心の半径）/ `falloffDeg`（周辺への遷移幅）
- 位置の制御は3モード
  - `fixed` — 画面中央固定（比較用のベースライン）
  - `mouse` — マウス追従（カメラ無しでデモできる。**Phase 2の前にここで体験の質を詰める**）
  - `gaze` — Phase 2

**完了条件**: マウス追従で文章を読もうとしたとき、「読みたい行が読めない」感覚が出ること。

**実装メモ（描画方式は当初案から変更）**

当初は「σ違いの本文を N 枚重ねて半径マスクでクロスフェード」で書いたが、
`backdrop-filter` を使う方式に変えた。本文の描画は1回きりで、その上に
透明な層を6枚重ね、各層に `backdrop-filter: blur()` と半径マスクをかける。
内側ほど層が重なってぼけが強くなる。

理由は、N枚方式だと本文全体を N 回ラスタライズし、しかも文書はスクロールする
長さぶんの面積を持つため。`backdrop-filter` の層は `position: fixed` で
ビューポートだけを覆うので、面積が画面サイズに固定される。

**層の置き方は半径の等間隔**。当初は σ を等間隔に割っていたが、これだと
`curve > 1` のとき層が中心付近に密集し、外側に1枚も届かない。
「ぼける範囲 560px」と指定しても実際の効果は 278px で途切れていた。
半径で割れば指定範囲の全体に層が行き渡る。

各層の σ は、その帯での累積が profile の値に一致するよう逆算する。
ガウスぼかしの重ねがけは σ が二乗和の平方根で増えるので
`σ_k = sqrt(S_k² - S_(k-1)²)`。検算すると 9 層で最外周 560px、
各帯の累積が理論値と小数2桁まで一致する。

**プロファイルの形**: `σ = centerSigma * (1-t)^curve`。
以前は smoothstep だったが、あれは中心側の傾きが 0 なので
「一定にぼけた円」に見えてしまい、中心から少しずつ変化する感じが出ない。

**未確認**: 実際の操作時のフレームレートは測れていない。検証環境では
ブラウザペインが `visibilityState: hidden` のままで `requestAnimationFrame` が
発火しないため、連続的な追従の滑らかさは実機で触って判断する必要がある。

### Phase 1 — 計測データを反映

`localStorage` の `HistoryRecord` を読み、48点の `radiusDeg` からぼかし量の面を作る。

- 補間は `Result.tsx` にある**ガウス重み付きIDWをそのまま使う**。
  現在 `Result.tsx` に埋め込まれているので、`src/fieldMap.ts` として切り出して共用する
- `radiusDeg → ぼかしσ` の対応は**ヒューリスティック**であることを明記する。
  「気付くのに必要だった刺激サイズ」は「そこで分解できる最小の特徴サイズ」の代理指標なので、
  `σ_deg = k × radiusDeg` を出発点にし、`k` はUIで調整できるようにする。
  心理物理的に検証されたマッピングではない
- 履歴から測定回を選べるようにする（複数回測っている場合の比較）

**視角の単位に注意。** 計測は視距離20cm前提だが、シミュレータを見る距離は違う。
マップは**視角（度）で保持**し、ピクセルへの変換はシミュレータ側の視距離設定で行う。
`pxPerDeg()` は既にあるので、シミュレータ用の `Settings` を別に持たせる。
20cmで測って60cmで体験すると、同じ視角が約3倍のピクセルを占める。

**完了条件**: 自分の計測結果でぼかしが変わり、`Result.tsx` のマップと形が一致する。

### Phase 2 — 視線追従

`../gaze-tracker` を統合する。ここが本命であり、一番難しい。

**遅延が最大の敵。** 実際の中心暗点は網膜固定なので遅延ゼロで動く。
シミュレータに遅延があると、サッケードのたびに「一瞬見えてから隠れる」ことになり、
これは現実には絶対に起きない現象で、体験としては嘘になる。

gaze-tracker の実測値は accuracy 1.5〜1.8°、precision 0.23〜0.46°、
ただし**適応EMA使用時の整定時間が約900ms**。これは視線カーソル用のチューニングで、
この用途にはそのまま使えない。

- **平滑化のトレードオフが逆転する。** カーソル用途ではジッタを嫌って重く平滑化したが、
  暗点の場合、位置が多少揺れても遮蔽は成立する一方、遅延は必ず「見えてはいけないものが見える」
  という形で破綻する。**遅延最小・ジッタ許容**の設定を別に用意する
- **ぼかし半径に安全マージンを足す。** 追従誤差1.5〜1.8°ぶん、計測値より広くぼかす。
  そうしないと推定誤差でたまたま中心が見えてしまう
- **フォールバック必須**: カメラ不可・キャリブレーション失敗時は `mouse` に落とす

**統合の技術的問題**: gaze-tracker は素のJS、こちらは React 19 + TS。
gaze-tracker 側の `src/core/` は DOM 非依存のモジュール群なので、
`pipeline.js` / `ridge.js` / `smoothing.js` を薄いラッパで呼ぶ形にする。
モノレポ化はしない（別プロジェクトのまま相対パス参照か、`file:` 依存）。

**運用コスト**: 体験するたびにキャリブレーション約30秒＋フルスクリーンが要る。
デモの導線としては重いので、`mouse` モードを常に選べるようにしておく。

**完了条件**: 視線を動かしても読みたい場所が読めない。マウスモードと体感が明確に違う。

## 描画方式

空間的に変化するぼかしが要るので、CSS `filter: blur()` 単体では足りない。

**採用**: 多段ぼかし＋放射状マスクのクロスフェード（foveated rendering の定石）

1. テキストを1枚のレイヤとして N 段階（例: σ = 0, 2, 4, 8, 16px）に事前ぼかし
2. 各段を、注視点からの距離に応じた α マスクで重ねる
3. 注視点が動いたらマスクだけ動かす（**再ぼかしは不要**＝毎フレーム安い）

段数は 5 前後で足りるはずだが、段の間で縞が見えるようなら増やす。

**却下した案**:
- WebGL シェーダで σ をテクスチャから引く — 品質は最上だが、
  この段階ではテキストのラスタライズとフォント品質の管理が増えるだけ
- DOM 要素ごとに `filter` — 文字単位で切り替わり、連続的な視野にならない

## 「ぼかし」で足りるのか

LHON の中心視野障害は単なるぼけではなく、**コントラスト感度の低下と暗点**を含む。
ガウスぼかしは高空間周波数の除去なので視力低下の第一近似としては妥当だが、
以下は Phase 0 では再現しない。**やるとしたら Phase 3 以降**。

- 中心の輝度低下・彩度低下（washed out）
- 絶対暗点（見えない）と相対暗点（見えにくい）の区別
- 計測が示す**非対称な**欠損形状（`Result.tsx` のマップは既に非対称を捉えている）

Phase 1 で計測データを入れた時点で、少なくとも形状の非対称性は反映される。

   （`blurProfile.ts`。度に移すときはここ一箇所を差し替える）

## 進め方の提案

Phase 0 → Phase 1 の順で、**Phase 0 の時点で一度触って**もらうのが良いと思う。
「中心がぼけたテキスト」が体験としてどのくらい効くかは、パラメータを触ってみないと分からない。
視線追従は効果が大きいぶん実装コストも遅延の問題も大きいので、
Phase 0/1 で体験の骨格が確認できてから着手したい。
